# 시스템 아키텍처 문서

## 1. 전체 구성도

```
┌─────────────────────────┐
│   Flutter 앱 / 모바일 웹   │
└───────────┬──────────────┘
            │ REST API (HTTPS)
            │ WebSocket (STOMP) - 실시간 방/라운드 이벤트
            ▼
┌─────────────────────────┐
│     Spring Boot 백엔드    │
│  ┌─────────────────────┐ │
│  │ 방/유저/라운드 상태   │ │──── PostgreSQL (오프체인 데이터)
│  │ 관리 서비스          │ │
│  └─────────────────────┘ │
│  ┌─────────────────────┐ │
│  │ 사진 업로드 서비스    │ │──── IPFS (사진 원본 저장, CID 반환)
│  └─────────────────────┘ │
│  ┌─────────────────────┐ │
│  │ 릴레이 지갑 서비스    │ │──── Polygon Amoy 테스트넷
│  │ (트랜잭션 서명/전송)  │ │      스마트 컨트랙트
│  └─────────────────────┘ │
└─────────────────────────┘
```

## 2. 컴포넌트 개요

### 2.1 클라이언트 (Flutter)

- iOS/Android 크로스플랫폼 앱 + 반응형 모바일 웹을 동일 코드베이스로 대응.
- 방 목록/입장, 카메라 촬영·업로드, 가격 예측 입력, 실시간 진행 상황(제출 현황, 리빌 결과) 표시를 담당.
- 사용자는 별도의 암호화폐 지갑 앱이나 시드 문구 관리 없이, 서비스 계정(이메일/소셜 로그인 등)만으로 게임에 참여한다.

### 2.2 백엔드 (Spring Boot)

오프체인 상태 관리, 온체인 트랜잭션 중계, 실시간 이벤트 브로드캐스트를 담당하는 중심 서버.

- **방/유저/라운드 관리**: 방 생성·입장, 참가자 로테이션 순서, 라운드 진행 상태 등 게임의 오프체인 메타데이터를 PostgreSQL에 저장.
- **사진 업로드 서비스**: 클라이언트로부터 받은 사진을 IPFS에 업로드하고 반환된 CID(Content Identifier)를 라운드 데이터와 함께 기록. 클라이언트에는 CID/게이트웨이 URL을 전달.
- **릴레이 지갑 서비스**: 사용자가 가스비를 직접 지불하지 않도록, 백엔드가 관리하는 릴레이 지갑이 사용자 요청을 대신 온체인 트랜잭션으로 전송한다(커밋 등록, 리빌 검증, 정산, 보상 지급). 사용자별 요청은 서명/검증을 거쳐 위임 실행되며, 자세한 신뢰 모델은 [smart-contract.md](smart-contract.md)의 "지갑 추상화" 절 참고.
- **실시간 이벤트 브로드캐스트**: WebSocket(STOMP)으로 방 참가자 입장/퇴장, 사진 공개, 예측 제출 현황, 리빌 결과, 라운드 종료 등을 실시간 전파.

### 2.3 데이터 저장소

| 저장소 | 저장 데이터 | 비고 |
| --- | --- | --- |
| PostgreSQL | 유저 계정, 방/참가자 정보, 라운드 메타데이터(출제자, 상태, 시간), 최종 순위 캐시 | 오프체인, 빠른 조회용 |
| IPFS | 출제 사진 원본 | 콘텐츠 주소(CID) 기반, 변조 불가능 |
| Polygon Amoy 온체인 | 커밋 해시, 공개된 예측값, 라운드 정산 결과, 보상 토큰 지급 내역 | 신뢰가 필요한 게임 핵심 데이터 |

### 2.4 블록체인 레이어 (Polygon Amoy 테스트넷)

- EVM 호환 체인으로 Solidity 스마트 컨트랙트를 배포한다. 낮은 가스비와 빠른 블록 생성 시간 덕분에 라운드마다 발생하는 커밋/리빌/정산 트랜잭션을 게임 템포에 맞게 처리할 수 있다.
- 예측값의 커밋-리빌 처리, 2등 판별 정산, ERC20 보상 토큰 지급의 신뢰 기반 로직을 담당한다. 상세 설계는 [smart-contract.md](smart-contract.md) 참고.

## 3. 주요 데이터 흐름

### 3.1 사진 출제

```
클라이언트(출제자) → [사진 업로드] → 백엔드
백엔드 → IPFS 업로드 → CID 수신
백엔드 → (릴레이 지갑) → 온체인 라운드 생성 트랜잭션 (CID 해시 기록)
백엔드 → WebSocket 브로드캐스트 → 전체 참가자에게 사진 공개
```

### 3.2 예측 제출 (커밋)

```
클라이언트(참가자) → 예측 가격 + salt 생성 → 커밋 해시 계산
클라이언트 → 백엔드 → (릴레이 지갑) → 온체인 커밋 등록 트랜잭션
백엔드 → WebSocket 브로드캐스트 → "N/총원 제출 완료" 진행률 갱신
```

### 3.3 공개(리빌) 및 정산

```
전원 제출 완료 또는 제한시간 도달
→ 클라이언트가 각자 보관 중인 (가격, salt)를 백엔드로 전송
→ 백엔드 → (릴레이 지갑) → 온체인 리빌 트랜잭션 (커밋 해시 검증)
→ 전원 리빌 완료 시 → 온체인 정산 트랜잭션 (2등 판별, 승자 결정)
→ 온체인 → ERC20 보상 토큰 승자 지급
→ 백엔드 → WebSocket 브로드캐스트 → 결과 및 다음 라운드 안내
```

## 4. 신뢰 모델 요약

- **누가 예측값을 볼 수 있는가**: 리빌 전에는 온체인에 해시만 존재하므로 백엔드/운영자를 포함해 누구도 원문 값을 알 수 없다.
- **백엔드가 신뢰를 요구하는 지점**: 릴레이 지갑이 사용자 대신 트랜잭션을 전송하지만, 커밋 해시·리빌 검증·정산 로직은 모두 스마트 컨트랙트 안에서 실행되므로 백엔드가 결과를 임의로 조작할 수 없다. 백엔드가 통제하는 것은 "트랜잭션을 언제 전송하는가"(오프체인 타이밍)뿐이다.

## 5. 미정 사항

- [ ] 릴레이 지갑의 구체적 구현 방식(자체 서명 vs. 메타트랜잭션 표준(EIP-2771) 사용 여부)
- [ ] IPFS 핀닝(pinning) 서비스 선정 (예: Pinata, Infura IPFS 등)
- [ ] 서버 배포 환경(클라우드/온프레미스) 및 CI/CD 파이프라인
